## 2. 分层与依赖方向

```text
constants → types → utils → core → api-client
                                 ↓
                    apps（api / miniapp / admin / mobile）
```

### 2.1 每层的职责与禁止事项

| 层 | 职责 | 明确禁止 |
|---|---|---|
| `constants` | 枚举、常量、阈值 | 任何依赖 |
| `types` | 领域类型、DTO | 运行时逻辑 |
| `utils` | 日期、字符串、数值、Result、错误类型 | 业务语义 |
| `core` | 业务规则（纯函数） | UI、数据库、网络、平台 API |
| `api-client` | HTTP 封装、错误映射、重试 | UI、具体平台 API（通过适配器注入） |
| `apps/*` | UI、路由、持久化、平台能力 | 重复实现 core 里已有的规则 |

### 2.2 为什么这样切

**if 业务规则散落在各端**，同一件事（比如「护照在准备阶段」）就会有三份实现：

- 小程序认为过期阈值是 90 天；
- App 认为是 30 天；
- 后端认为是 180 天。

结果是「同一次旅行，三个端显示三套结果」。把规则下沉到 `core` 之后，
三端只能调用同一个函数，**从结构上消除了漂移的可能**。

**代价**：`core` 里不能直接 `import Taro` 或 `import { PrismaClient }`。
所有平台能力必须由调用方注入。这也是 `api-client` 设计 `HttpAdapter` 接口的原因。

### 2.3 依赖检查方式

```bash
pnpm typecheck   # 任意反向依赖都会导致编译失败
```

## 3. 关键设计决策

### 3.1 `＋ / ✓` 状态必须来自真实 PlanItem

**需求**：日本与韩国攻略里都出现「护照」，两个国家都点 `＋` 后整个 Trip 只能有一条。

**实现**：

```text
packages/core/src/plan/planDedupe.ts     ← 纯函数：buildDedupeKey / isDuplicatePlanItem
apps/miniapp/src/features/**             ← 页面调用它判断显示 ＋ 还是 ✓
apps/api/src/modules/trip/trip.service.ts ← 服务端再次校验并返回幂等结果
prisma/schema.prisma                     ← @@unique([tripId, dedupeHash]) 数据库兜底
```

**三层防护**的原因：客户端可能因为并发、离线、缓存过期而判断错误；
服务端是权威；数据库约束是最后一道防线。任何一层单独存在都不够。

**去重键的构造规则**：

```text
1. 有 dedupeKey（后台配置）→ 用它（不含国家）        → k:passport
2. 无 dedupeKey 但有 sourceId → 用来源键（含国家）    → s:ATTRACTION:JP:sensoji
3. 都没有 → 用「类型 + 阶段 + 归一化标题」
```

第 2 条**必须含国家**：日本和韩国各有一个「中央公园」时，它们是两个景点而不是重复项。

### 3.2 阶段切换不做日期自动切换

**需求**：`系统提示 + 用户确认`。

**实现**：`getCurrentTripStage` 的判定优先级是

```text
1. COMPLETED → 归程阶段
2. 用户已确认的状态（PREPARING/DEPARTING/TRAVELING/RETURNING）→ 直接采用
3. DRAFT → 准备阶段
4. 兜底：按日期推断
```

**关键点**：**用户确认的状态优先于日期推断**。这意味着即使用户在出发日仍停留在准备阶段，
系统也只会「提示」而不会擅自切换。`getStageSwitchPrompt` 只提示**向前推进**，
不主动提示回退（回退由用户手动操作）。

### 3.3 签证匹配是「护照地区 + 目的地」

**需求**：同一目的地对不同护照结论不同（CN → JP 需签证，SG → JP 免签）。

**实现**：三级兜底

```text
exact           CN + JP   ← 优先
region-fallback CN + *    ← 「中国大陆护照的通用政策」
global-fallback * + JP    ← 「所有护照去日本的政策」
none            → 返回空视图
```

**为什么顺序是这样**：对用户而言「我这本护照的通用规则」比「所有护照对这个国家的规则」更贴近自身情况。

**客户端的连带影响**：签证缓存 key **必须**含护照地区（`visa_CN_JP`）。
用户改护照地区后必须清掉旧地区的全部签证缓存，否则会拿着上一个护照的结论继续展示。

### 3.4 分模块内容版本

**需求**：后台只改签证时，客户端只刷新签证缓存，不要全量重下。

**实现**：

```text
GET /api/v1/content/version → { country: 12, visa: 28, attraction: 53, ... }
客户端：逐模块比较 → 只拉取变化的模块 → **成功后**再写回本地版本号
```

两个极易写错的点：

1. **顺序**：必须先拉数据成功、再写版本号。反过来的话请求失败时本地版本已经"新"了，
   客户端会永久展示旧内容，而且永远不会再尝试刷新。
2. **本地缺失 ≠ 必然变化**：`diffContentVersion` 对「本地没记录 且 服务端版本为 0」
   判定为**无变化**。否则每个从未启用的模块都会触发一次无意义请求。

### 3.5 3D 地球：投影数学与渲染分离

**需求**：视觉像 3D，交互必须丝滑；低端机保证稳定 30 FPS。

**实现**：

```text
packages/core/src/common/geometry.ts         ← 球面投影、遮挡判定（纯函数）
apps/miniapp/src/canvas/globe/globe-state.ts ← 手势状态机（纯函数）
apps/miniapp/src/canvas/globe/globe-renderer.ts ← 只负责画
apps/miniapp/src/canvas/globe/GlobeCanvas.tsx   ← 组件：接线 + rAF 循环
```

**为什么必须分离**：如果投影写在渲染函数里，「地球转反了」「点不中国家」这类问题
只能靠肉眼在真机上发现。分离之后它们全变成可断言的数值，
而且我们在实现过程中确实靠单测抓出了三个真实缺陷：

1. `withTimeout` 有 AbortController 时只 abort 不 reject → 超时形同虚设；
2. 遮挡判定的相机方向被写死成 `+x` → 拖动时可见性完全不变，能点到地球背面的国家；
3. 自动旋转无条件返回 `moving: true` → rAF 永不停止，切走后仍在满帧重绘耗电。

**性能策略**：

| 手段 | 效果 |
|---|---|
| 静止时 `moving=false`，取消 rAF | 大部分时间完全不重绘 |
| `continuousAutoRotate` 与 Tab 激活状态绑定 | 切走后自动停帧，但不销毁 Canvas |
| 连续 45 帧 > 40ms 才降一档画质 | 避免单次 GC 抖动导致画面闪变 |
| 地理数据本地打包 | 首屏不依赖网络 |
| 兜底数据集 | 即使 JSON 打包遗漏，地球仍能转、能吸附 |

**画质降级只影响视觉特效**（大气层 / 粒子 / 阴影 / 网格），
拖动、旋转、吸附最近大陆、选择国家这四项**在任何档位都保持开启**。

### 3.6 图片上传：压缩 + 不保存原图

**需求**：上传 → 校验 → 解码 → 缩放 → 压缩 → 转 WebP → 保存 → **丢弃原图**。

**实现要点**：

| 环节 | 处理 |
|---|---|
| 文件缺失 | 在**解码之前**拒绝，不浪费 CPU |
| 类型不支持 | 校验 MIME **与魔数**，防止 `.txt` 改名成 `.png` |
| 超过 5MB | 拒绝并给出「当前 8.6 MB」这类具体信息 |
| 解码失败 | `IMAGE_PROCESS_FAILED`，可展示原因，**不写任何文件** |
| 存储写入失败 | 尝试清理残留文件后再抛错 |
| 路径 | `buildSafeRelativePath` 过滤 `..`，并二次校验未逃出根目录 |

**文件名生成**：`{用途}-{时间戳36进制}-{sha256前8位}-{随机4位}.webp`
同时解决可读性、天然去重与并发碰撞。

### 3.7 存储抽象（为将来迁 OSS 留口）

```ts
interface StorageService {
  upload(input): Promise<StoredFile>
  delete(relativePath): Promise<boolean>   // 幂等：不存在返回 false 而非抛错
  getUrl(relativePath): string
  exists(relativePath): Promise<boolean>
  readonly rootDir: string
}
```

接口刻意做得很小。实际实现有 `LocalStorageService`（本地磁盘）与
`InMemoryStorageService`（测试替身）。未来换 `AliyunOSSStorageService` 时业务代码零改动。

### 3.8 统一错误响应

**目标**：客户端只解析一种错误格式。

```json
{ "success": false, "code": "VALIDATION_FAILED", "message": "国家代码必须是两位大写字母",
  "details": { "issues": [...] }, "requestId": "...", "timestamp": "..." }
```

`code` 是**稳定的机器可读错误码**（不是中文文案），客户端据此分支；`message` 才用于展示。

**必须处理的 6 类异常来源**：

1. 本项目的 `AppError`（core / api-client 抛出）
2. Prisma 已知错误（`P2002` 唯一冲突 → 409、`P2025` 不存在 → 404、`P2003` 外键 → 400）
3. NestJS `HttpException`
4. 请求体校验失败（Zod → 字段级 `issues`）
5. 运行时 `TypeError` 等程序缺陷 → 500 且**不返回堆栈**
6. 其它未知值（字符串 / null）

**5xx 一律使用通用文案**，绝不把 SQL、文件路径或依赖栈泄漏给客户端。

### 3.9 客户端网络兜底

| 场景 | 行为 |
|---|---|
| 网络不可达 | `NETWORK_FAILED`，可重试，可回退缓存 |
| 请求超时 | 默认 10s；**无 AbortController 的环境也生效**（Promise.race 兜底） |
| 5xx / 429 / 408 | 指数退避 + ±25% 抖动，最多 2 次 |
| 4xx（其它） | **不重试** |
| POST / PATCH / DELETE | 默认不重试（防重复创建） |
| 401 | 触发注入的回调（清登录态 → 跳登录） |
| 响应是 HTML | `RESPONSE_PARSE_FAILED`，绝不把 HTML 当数据 |

**抖动为什么是乘法**：`min(base·2^n, max)·(0.75~1.25)`。
加法抖动在 base 很小（如 300ms）时无法有效打散重试时间，仍会出现惊群。

### 3.10 主 Tab 单页 Shell

**需求**：三个主 Tab 切换不能重新创建页面（否则 3D 地球会被销毁重建）。

**实现**：

```text
pages/dashboard/index.tsx
├── .tabViewport（overflow: hidden）
│   └── .tabStage（display:flex; width:300vw; translate3d(-n*100vw)）
│       ├── .tabPane（100vw）→ ScrollView → MapTabContent
│       ├── .tabPane（100vw）→ ScrollView → PlanTabContent
│       └── .tabPane（100vw）→ ScrollView → ProfileTabContent
└── FloatingTabBar（position: fixed）
```

- 主 Tab 切换**只改 `activeTab`**，不使用 `navigateTo / redirectTo / switchTab / reLaunch`；
- 三个 Tab **始终挂载**；
- 每个 Tab 有自己的纵向 `ScrollView`，避免"最高的页面撑高整个 Stage"；
- `.tabScroll` 统一 `padding-bottom: 200px`，防止内容被悬浮 TabBar 遮挡；
- `will-change: transform` **只**加在 `.tabStage` 上，不给普通组件滥用。

二级页面（国家详情、设置等）仍然正常使用 Taro 路由。

## 4. 数据流

### 4.1 读取静态内容（Cache First + Background Refresh）

```text
页面请求
  ↓
Service 查本地缓存 ──命中──→ 立即返回缓存 + meta.fromCache=true
  │                              ↓（不阻塞）
  │                          后台请求接口 → 成功则更新缓存
  └─未命中→ 请求接口
              ↓
         成功 → 写缓存 → 返回
         失败 → 有旧缓存？有则返回旧数据并记日志
                          无则把错误抛给页面
```

**为什么不"过期就丢弃"**：过期只代表「需要后台刷新」，不代表「不能用」。
直接白屏等网络是最差的体验。

### 4.2 `＋` 的完整链路

```text
用户点击 ＋
  ↓
页面用 buildDedupeKey 计算键 → 查本地 PlanItem 判断当前是 ＋ 还是 ✓
  ↓（点击 ＋）
POST /trips/:tripId/plan-items
  ↓
TripService.addPlanItem
  ├─ 查 dedupeKey 是否已存在 → 存在则返回 created:false（幂等，不抛 409）
  ├─ 不存在则创建，sortOrder 追加到该阶段末尾
  └─ 并发冲突（P2002）→ 重新查一次并返回已存在的那条
  ↓
客户端用返回值更新本地列表与缓存，Toast「已加入准备计划」
```

`✓` 的删除同样返回完整快照，客户端据此实现「已从计划移除 [撤销]」——
撤销就是拿快照再调一次 `POST /plan-items`，因为 dedupeKey 保证不会产生重复。

## 5. 已知取舍

| 决策 | 取舍 | 后续演进 |
|---|---|---|
| 地理数据用「中心点 + 椭圆采样」示意轮廓 | 体积小、首屏快，但不是真实国界 | 换 `continents.min.json` 为真实矢量，渲染层无需改动 |
| 后台鉴权用 HMAC 签名令牌 | 零依赖、逻辑透明 | 换 `@nestjs/jwt` 只需替换 `signToken` / `verifyToken` |
| 内容健康度实时计算 | 实现简单、结果一定准确 | 数据量上来后改定时任务预计算 |
| 内存模式 + 接口 + 工厂装配 | 让 service 可在无数据库环境完整单测 | 生产使用 Prisma 实现，接口不变 |
| App 端只提供骨架 | 先把共享层价值验证清楚 | 按小程序端同一模式补页面 |
| `expect` 兼容层只实现常用匹配器 | 覆盖本项目全部断言 | 未实现的匹配器会**显式报错**，不会静默通过 |
