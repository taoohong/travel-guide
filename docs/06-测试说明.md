# 测试说明

> `pnpm test` 会运行 546 个用例。本文说明测试策略与如何新增用例。

---

## 1. 测试策略

| 层次 | 范围 | 工具 | 侧重点 |
|---|---|---|---|
| 单元测试 | `utils` / `types` / `constants` | Vitest | 日期边界、去重键归一化、Result 与错误归类 |
| 单元测试 | `core` | Vitest | 业务规则清单逐条 + 边界（空 Trip / 跨大陆 / 重复 / 过期） |
| 单元测试 | `api-client` | Vitest + 假适配器 | 超时、重试退避、4xx 不重试、非 JSON 响应、401 回调 |
| 单元测试 | `apps/api` | Vitest | Prisma 错误映射、图片流水线、签证匹配、计划幂等 |
| 单元测试 | `apps/miniapp` | Vitest | 地球投影自洽性、手势状态机、缓存失效、画质降级 |

### 为什么大量测试集中在 `core`

`core` 是**唯一被三端共同依赖**的层。它出错时，小程序、App、后端会**同时**出错，
而且三处表现可能不一致（例如小程序认为 90 天过期、后端认为 180 天），排查成本极高。

因此策略是：**把规则尽可能下沉到 `core`，然后用测试把它锁死**。
各端的测试只需要验证"接线是否正确"。

### 测试替代（Test Double）策略

`apps/api` 的所有 service 都通过**接口 + 工厂**注入依赖，因此可以在没有数据库、
没有原生图片库的环境里被完整测试：

| 真实依赖 | 测试替身 | 文件 |
|---|---|---|
| PostgreSQL / Prisma | `InMemoryTripRepository` 等 | `apps/api/src/modules/*/**.repository.ts` |
| 本地磁盘 | `InMemoryStorageService` | `apps/api/src/modules/media/storage.service.ts` |
| sharp（原生） | 假 `ImageEngine` | `apps/api/tests/media.test.ts` |
| 真实网络 | `createMemoryAdapter` | `packages/api-client/src/adapters.ts` |

**内存实现必须与真实实现语义一致**——否则测试通过但线上失败。
因此内存仓储刻意实现了数据库的两个关键行为：

1. `(tripId, dedupeHash)` 唯一约束（冲突时抛 `code = 'P2002'`）；
2. 深拷贝返回（真实数据库每次查询都返回新对象，若内存实现返回内部引用，
   "保存两次"会互相污染，从而掩盖真实环境才有的 bug）。

## 2. 运行方式

### 首选：Vitest

```bash
pnpm test:vitest              # 单次运行
pnpm test:vitest:watch        # watch 模式
pnpm test:vitest --ui         # 需要 @vitest/ui
```

### 回退：零依赖运行器

Vitest 依赖 esbuild 的原生二进制，在部分受限环境（CI 沙箱、
无法运行原生二进制的容器）会启动失败。此时用内置回退运行器：

```bash
pnpm test
# 等价于：
node --import ./tools/domless/register-novitest.mjs \
  --test --experimental-test-isolation=none \
  "packages/*/tests/*.test.ts" "apps/api/tests/*.test.ts" "apps/miniapp/tests/*.test.ts"
```

### 回退运行器的实现

| 能力 | 实现方式 |
|---|---|
| 模块解析（`@travel-guide/*` 别名） | `module.registerHooks` 的 `resolve` 钩子，扫描 `packages/*/package.json` |
| 无扩展名相对导入 | 自动补全 `.ts` / `/index.ts` |
| TypeScript 转译 | `module.stripTypeScriptTypes({ mode: 'transform' })` |
| `expect` / `describe` / `it` | 自实现最小兼容层（`tools/domless/expect.ts`） |
| `import { expect } from 'vitest'` | 重定向到内置 shim（`tools/domless/vitest-shim.ts`） |

> **为什么用 `transform` 而不是 `strip`**：后端代码里有构造器参数属性
> （`constructor(private x: T)`），strip-only 模式会直接报
> `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX`。
>
> 代价是 `transform` 不产出 `emitDecoratorMetadata`，
> 因此回退运行器下需要**显式 `new`** 构造服务（测试里本来就是直接 new）。
> NestJS 的 DI 由 `pnpm api:dev` 走真实编译产物。

### ⚠️ 回退运行器会主动检测「忘记 await」

```ts
// ❌ 危险：不会真正执行断言，但测试"通过"了
it('应该拒绝', () => {
  expect(promise).rejects.toThrow('boom')
})

// ✅ 正确
it('应该拒绝', async () => {
  await expect(promise).rejects.toThrow('boom')
})
```

第一种写法是最危险的一类测试 bug——**假绿**。
回退运行器会检测用例函数是否返回了 Promise，并直接让其失败：

```text
本用例返回了 Promise 但没有被 await。请写成
`it("...", async () => { await expect(...).rejects... })`——
否则断言不会真正执行，测试会假绿。
```

Vitest 本身能正确处理这两种写法，但为了两种运行器行为一致，
**本项目统一要求写 `await`**。

## 3. 编写测试的约定

### 3.1 使用共享数据工厂

```ts
import { makeTrip, makePlanItem, makeVisaPolicy } from '../../../tests/factories'

// 只传测试真正关心的字段，其余有合理默认值
const trip = makeTrip({ status: 'TRAVELING', startDate: '2026-10-01' })
```

> **注意工厂的 `withDefaults` 语义**：显式传 `null` 会**保留**，
> 传 `undefined` 才用默认值。
>
> 为什么强调这一点：如果工厂写成 `overrides.lastVerifiedAt ?? '2026-09-01'`，
> 那么 `makeVisaPolicy({ lastVerifiedAt: null })`（想表达「从未确认」）
> 会被悄悄替换成默认日期，**「从未确认」这条分支永远测不到**。
> 我们在实现过程中就踩过这个坑。

### 3.2 断言要保留"为什么"

```ts
// ❌ 只有 what，将来没人敢改
expect(progress.percent).toBe(50)

// ✅ 说清业务含义，未来改规则时知道该不该同步改测试
// 日本与韩国攻略都含「护照原件」，dedupeKey 相同 → 一个 Trip 只创建一次
expect(await tripService.listPlanItems(trip.id)).toHaveLength(1)
```

### 3.3 一个用例只验证一个行为

失败时能立刻定位原因。如果一个用例同时验证"签证匹配 + 缓存失效 + 日志记录"，
失败信息无法告诉你哪一环坏了。

### 3.4 必测的边界

| 类别 | 例子 |
|---|---|
| 空值 | `null` / `undefined` / 空数组 / 空字符串 |
| 非法格式 | `'2026-02-30'`、`'bad'`、`countryCode: 'JPN'` |
| 边界值 | 天数计算的含头含尾、闰年 2/29、跨 ±180° 经度 |
| 并发 | 重复点击 `＋`、唯一约束冲突 |
| 网络 | 超时、5xx、4xx、非 JSON 响应、无 AbortController 环境 |
| 存储 | JSON 损坏、存储被禁用、配额写满 |

### 3.5 时间相关测试必须注入时间

```ts
// ❌ 依赖真实时钟：将来某天会突然失败
expect(isVisaPolicyStale(policy)).toBe(true)

// ✅ 注入 today
expect(isVisaPolicyStale(policy, 90, '2026-09-20')).toBe(true)
// 或通过 service 的 options
await visaService.coverage({ today: '2026-09-20' })
```

## 5. 测试帮我们抓到的真实缺陷

这些都是在实现过程中**靠单测而非肉眼**发现的，记录在此以说明测试的价值：

| # | 缺陷 | 后果 | 发现方式 |
|---|---|---|---|
| 1 | `withTimeout` 在有 AbortController 时只 `abort()` 但不 reject | 若底层实现忽略 signal（自定义适配器、部分小程序版本），超时**完全失效**，调用方会一直等到请求自然结束 | 「超时抛 REQUEST_TIMEOUT」用例 |
| 2 | 遮挡判定的相机方向被写死为 `+x` | 拖动地球时**可见性完全不变**，用户能点到地球背面的国家 | 「旋转地球会改变可见性」用例 |
| 3 | 自动旋转无条件返回 `moving: true` | rAF 循环**永不停止**，切到其它 Tab 后地球仍在后台满帧重绘，白耗电 | 「地图 Tab 被切走时不再占用动画帧」用例 |
| 4 | 投影的旋转顺序（yaw/pitch）与相机方向不一致 | 默认视角看不到目标国家，点击位置与显示国家错位 | 「投影到屏幕正中的点必然可见」不变量用例 |
| 5 | 测试工厂用 `overrides.x ?? 默认值` | 显式传 `null` 被吞掉，「从未确认」「无城市」等分支永远测不到 | 「KR 从未确认 → stale」用例 |
| 6 | 内存仓储返回内部对象引用 | 「保存两次」互相污染，掩盖真实环境才有的 bug | 「重复保存会覆盖而不是新增」用例 |
| 7 | `diffContentVersion` 把「本地缺失 + 服务端为 0」判为变化 | 每个从未启用的模块都触发一次无意义请求 | 「本地只记录一部分模块」用例 |
| 8 | 回退运行器对未 `await` 的用例静默通过 | **假绿**：测试全绿但什么都没验证 | 主动加入检测 |

第 5 与第 8 条尤其值得注意：它们不是产品代码的 bug，
而是**测试代码自身的 bug**——后者比前者更危险，因为它会让你误以为一切正常。

## 6. 构建阶段才发现的问题

静态类型检查通过 ≠ 能构建成功。下面这些只有真正跑一次构建才会暴露：

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 开发者工具报「未找到 app.json」 | `project.config.json` 缺 `miniprogramRoot`，工具去项目根找 `app.json` | 设为 `"dist/"` |
| 2 | 构建报 `Cannot find module '@babel/preset-react'` | `babel-preset-taro` 的预设不是自动安装的传递依赖 | 显式加进 `devDependencies` |
| 3 | 构建报 `Module parse failed: Unexpected token` | webpack 默认排除 `node_modules`，共享包被当普通 JS 解析 | `config/index.ts` 加 `mini.compile.include` |
| 4 | 构建报 resolve `destination-detail.scss` 失败 | Taro 按模块名解析样式，`xxx.scss` 与目录名不匹配 | 统一重命名为 `index.scss` |
| 5 | NestJS 产物启动即崩 `Cannot read properties of undefined` | `TOKENS` 定义在 `app.module.ts`，与 controller 形成循环依赖 | 抽出到 `common/tokens.ts` |
| 6 | `node dist/main.js` 报 `ERR_MODULE_NOT_FOUND` | 共享包产出 ESM 无扩展名导入，Node ESM 要求显式 `.js` | 共享包改为编译为 CommonJS |

## 7. 只有「真机/模拟器运行」才会暴露的问题

比构建更进一步：构建成功 ≠ 能跑起来。

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 启动即崩 `Cannot read properties of undefined (reading 'taroDocumentProvider')`，堆栈里出现 `core-js-pure` | `babel.config.js` 里多写了 `useBuiltIns: 'usage'`，`@babel/preset-env` 在每个模块顶部注入 polyfill，打乱 webpack 模块求值顺序，`@tarojs/runtime` 尚未导出就被访问 | 删掉该选项，回到 `babel-preset-taro` 默认值（`useBuiltIns=false`）；包体同时从 653KB 降到 520KB |
| 2 | devtools 报 `在项目根目录未找到 app.json` | `project.config.json` 缺 `miniprogramRoot` | 设为 `"dist/"` |
| 3 | `Cannot find module '@babel/runtime'`（潜在） | `@babel/plugin-transform-runtime` 生成的 helper 会 import 它，但它只是传递依赖 | 在 `apps/miniapp/package.json` 显式声明 |

**第 1 条特别值得记住**：它的表现（`taroDocumentProvider` 未定义）看起来像是
Taro 运行时或版本兼容问题，很容易让人去翻 Taro 源码、换版本、找 issue；
但真正的原因是**我自己加的 Babel 选项**。

排查路径也很典型 —— 堆栈里 `core-js-pure` 的帧是最关键线索：
它不是 Taro 的代码，而是被 Babel 注入进来的，说明问题出在「谁把 polyfill 插到了模块顶部」。

**结论**：第三方脚手架（Taro / Next / CRA）的配置项默认值通常是互相配合过的，
不要为了「更省体积」而随手覆盖；要改就先查清楚它默认为什么这么设。
