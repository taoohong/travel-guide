# 数据模型

> 模型定义见 `apps/api/prisma/schema.prisma`。本文解释**为什么这样设计**。

---

## 1. 设计原则

1. **结构化优先**：内容一律拆成字段与关联表，不做「一个大富文本字段」。
   这是「内容与表现分离」的落地——后台只维护"内容是什么"，
   客户端决定"长什么样"。
2. **planMapping 内联**：每条可加入计划的攻略内容都带 `actionable` /
   `targetStage` / `itemType` / `scope` / `dedupeKey` 五个字段。
3. **版本与有效期齐全**：所有内容表都有 `version` / `status` /
   `effectiveFrom` / `effectiveTo` / `lastVerifiedAt`。
4. **去重有数据库兜底**：`PlanItem(tripId, dedupeHash)` 唯一约束。

## 3. 关键表说明

### 3.1 User / AuthIdentity —— 用户主档与登录身份分离

```prisma
model User {
  id               String   @id @default(cuid())
  uid              String   @unique @default(uuid())
  nickname         String
  avatarUrl        String?
  passportRegion   String   @default("CN")
  showPlanAddGuide Boolean  @default(true)
  locale           String   @default("zh-CN")
  createdAt        DateTime @default(now())
  updatedAt        DateTime @updatedAt
  identities       AuthIdentity[]
  trips            Trip[]
  tripMemberships  TripMember[]
  anchors          UserAnchor[]
}

model AuthIdentity {
  id             String   @id @default(cuid())
  userId         String
  provider       String
  providerUserId String
  createdAt      DateTime @default(now())
  updatedAt      DateTime @updatedAt

  @@unique([provider, providerUserId])
  @@index([userId, provider])
}
```

- `User.id` 是数据库内部主键，供 `Trip.userId`、`TripMember.userId` 等关系使用；`User.uid` 是稳定、唯一的用户 UID，由服务端生成并提供给客户端及新登录令牌使用。
- `nickname`、头像等是可变资料，只用于显示；昵称不唯一，也不参与身份匹配。
- `AuthIdentity` 保存认证提供方及其稳定主体标识。当前微信登录使用 `WECHAT_MINI_PROGRAM + OpenID`，开发登录使用 `DEVELOPMENT + A/B`。外部标识不直接充当旅行表的外键。
- `(provider, providerUserId)` 唯一，保证同一提供方身份只映射到一个用户；`(userId, provider)` 支持一个 UID 关联多个登录方式。
- 新提供方首次登录时创建独立用户。只有在新提供方完成服务端验证、且用户明确绑定后，才应把其身份关联到既有 UID；不能按昵称、邮箱文本或其他未验证资料自动合并账号。
- 历史 `User.openId` / `User.devKey` 已迁入 `AuthIdentity`，原 `User.id` 及旅行外键保持不变；旧令牌仍可在兼容期内解析。

### 3.2 Continent / Country

```prisma
model Country {
  code          String  @unique   // ISO 3166-1 alpha-2
  continentCode String
  latitude      Float
  longitude     Float
  online        Boolean @default(false)
  completeness  Int     @default(0)  // 0～100，健康度看板用
  ...
  @@index([continentCode, online])
}
```

**为什么 `completeness` 冗余存字段**：健康度看板要按完整度排序，
每次实时 join 六张表计算完整度会很慢。该字段由内容发布流程重算。

### 3.3 VisaPolicy —— 唯一键是「护照地区 + 目的地」

```prisma
model VisaPolicy {
  passportRegion         String
  destinationCountryCode String
  visaType               VisaType @default(UNKNOWN)
  ...
  @@unique([passportRegion, destinationCountryCode])
  @@index([lastVerifiedAt])
}
```

**这是全库最重要的约束之一**。如果把唯一键写成只有 `destinationCountryCode`，
中国大陆与新加坡的日本签证政策会互相覆盖——这是文档 9.2 明确要避免的错误。

`passportRegion` 允许 `*` 作为「所有护照地区的通用政策」，
匹配顺序由 `packages/core/src/visa/visaPolicy.ts` 决定：精确 → 地区 → 全局。

`@@index([lastVerifiedAt])` 支撑「超过 90 天未确认」的体检查询。

### 3.4 PackingItem / CountryPacking —— 全局事项库

```prisma
model PackingItem {
  code String @unique       // passport / universal_power_adapter
  universal Boolean @default(false)
  dedupeKey String?
}

model CountryPacking {
  countryCode   String
  packingItemId String
  @@unique([countryCode, packingItemId])
}
```

**设计动机**（文档 27 章）：如果把「护照」分别写进日本、韩国、法国三条记录，
不仅数据冗余，而且三处 `dedupeKey` 很容易写得不一致，
最终导致 Trip 里出现三条「护照」。

改为「全局事项库 + 国家只做关联」后：
- `dedupeKey` 只有一处定义；
- 新增国家时无需重写通用物品；
- 修改描述只需改一行。

### 3.5 PlanItem —— 去重的最后一道防线

```prisma
model PlanItem {
  tripId      String
  stage       PlanStage
  itemType    PlanItemType
  scope       PlanScope
  sourceType  PlanSourceType
  sourceId       String?
  sourceCountryCode String?
  dedupeKey      String?
  dedupeHash     String?      // 计算后的键，用于唯一约束
  sortOrder   Int
  done        Boolean @default(false)
  doneAt      DateTime?
  planDate    DateTime?

  @@unique([tripId, dedupeHash])
  @@index([tripId, stage])
}
```

**为什么需要 `dedupeHash` 而不直接用 `dedupeKey`**：

`dedupeKey` 是后台配置的**业务键**，可能为 null（用户自建项）；
去重还需要覆盖「来源键」与「标题归一化」两种情况。
因此服务端用 `packages/core` 的 `buildDedupeKey` 算出**统一的键**写入 `dedupeHash`：

```text
有 dedupeKey        → k:passport
无 dedupeKey 有来源 → s:ATTRACTION:JP:sensoji
都没有              → k:PACKING_ITEM:PREPARING:护照原件（归一化后）
```

`@@unique([tripId, dedupeHash])` 让并发点击 `＋` 时数据库直接拒绝第二条，
服务端捕获 `P2002` 后重新查询并返回已存在的那条（保持幂等语义）。

**注意**：`dedupeHash` 为 null 时唯一约束不生效（PostgreSQL 允许多个 NULL），
这正是我们想要的——无法判定重复的项一律允许新增。

### 3.6 TripDestination —— 支持多国家与回头行程

```prisma
model TripDestination {
  tripId      String
  countryCode String
  continentCode String
  cityCode    String?
  orderIndex  Int
  arrivalDate   DateTime?
  departureDate DateTime?
  isOrigin    Boolean @default(false)

  @@unique([tripId, orderIndex])
}
```

**为什么唯一约束在 `orderIndex` 而不是 `(countryCode, cityCode)`**：
用户可能走「日本 → 韩国 → 日本」的回头行程，
国家可以重复出现，但**顺序不能有空洞或重复**。
「国家 + 城市」的去重放在服务层（`trip.service.ts` 的 `addDestination`），
因为业务上允许同一国家不同城市。

### 3.7 ContentVersion —— 分模块版本

```prisma
model ContentVersion {
  module  ContentModule @unique
  version Int @default(0)
  changedByEntity String?
  changedById     String?
}
```

七行数据（`country` / `visa` / `attraction` / `transport` / `packing` / `travelTip` / `city`），
每次内容发布只递增对应模块的版本号。

### 3.8 OperationLog —— 字段级变更

```prisma
model OperationLog {
  action      OperationAction   // CREATE / UPDATE / DELETE / PUBLISH / UNPUBLISH / LOGIN
  targetType  String
  targetLabel String
  changes     Json @default("[]")   // [{ field, before, after }]
  requestId   String?
}
```

`changes` 由 `computeChanges()` 自动 diff 生成，并**过滤掉技术字段**
（`updatedAt` / `createdAt` / `version` / `id`）——
运营看日志时关心的是「最长停留从 60 改成 90」，不是「版本号 +1」。

### 3.9 MediaAsset —— 只存 URL

```prisma
model MediaAsset {
  path String @unique   // attractions/jp/a.webp（相对路径）
  url  String           // 完整可访问 URL
  width Int
  height Int
  bytes Int
  mimeType String
  usage MediaUsage
}
```

**不存二进制**。数据库只保存路径与元信息，图片本体在
`/data/travel-guide/uploads`（文档 30.1 明确要求**不放在代码目录**）。

`MemoryPhoto` 同理，只保存 `url` 与 `path`。

## 4. 索引设计

| 表 | 索引 | 支撑的查询 |
|---|---|---|
| `Country` | `(continentCode, online)` | 地图页按大陆筛选线上国家 |
| `VisaPolicy` | `(passportRegion, destinationCountryCode)` 唯一 | 签证精确匹配 |
| `VisaPolicy` | `(lastVerifiedAt)` | 90 天未确认体检 |
| `PlanItem` | `(tripId, dedupeHash)` 唯一 | 并发点击 `＋` 去重 |
| `PlanItem` | `(tripId, stage)` | 计划页按阶段分组 |
| `User` | `(uid)` 唯一 | 稳定 UID 查询 |
| `AuthIdentity` | `(provider, providerUserId)` 唯一 | 将登录提供方身份映射到唯一用户 |
| `AuthIdentity` | `(userId, provider)` | 查询用户已绑定的登录方式 |
| `Trip` | `(userId, status)` | 「我的」页按状态排序 |
| `Trip` | `(userId, startDate)` | 历史旅行按时间倒序 |
| `TransportOption` | `(countryCode, kind)` | 国家详情页按类型分组交通 |
| `Attraction` | `(countryCode, status)` | 景点列表（只查已发布） |
| `OperationLog` | `(createdAt)` | 日志页时间倒序 |
| `OperationLog` | `(targetType, targetId)` | 按对象查变更历史 |

## 5. 时间字段的三种语义

| 字段 | 含义 | 谁维护 |
|---|---|---|
| `createdAt` / `updatedAt` | 记录写入时间 | Prisma 自动 |
| `effectiveFrom` / `effectiveTo` | **政策自身**的生效区间 | 内容运营 |
| `lastVerifiedAt` | **人**最后一次确认内容准确的时间 | 内容运营 |

三者必须分别判断。一条政策可以同时是「仍然生效」但「已经 200 天没人核对」——
前者是业务事实，后者是运维指标。`checkVisaFreshness()` 同时返回
`effective` / `expired` / `notYetEffective` / `stale` 四个独立标志。

## 6. 迁移与种子数据

```bash
pnpm api:prisma:migrate     # 开发环境：生成迁移并应用
pnpm api:prisma:deploy      # 生产环境：只应用已有迁移
pnpm api:seed               # 写入示例内容
```

种子数据覆盖三个示例目的地（日本 / 韩国 / 法国），并刻意包含以下**验证场景**：

| 场景 | 数据 |
|---|---|
| 同一目的地不同护照结论不同 | `CN → JP` 需签证；`SG → JP` 免签 |
| 跨国家只创建一次通用材料 | 日本与韩国的「护照原件」`dedupeKey` 都是 `passport` |
| 纯信息不显示 `＋` | 旅行贴士的 `actionable = false` |
| 跨大陆行程 | 日本（亚洲）+ 法国（欧洲） |
| 回头行程允许同国家不同城市 | 目的地按 `orderIndex` 唯一，国家可重复 |

## 7. 后续演进

| 需求 | 方案 |
|---|---|
| 内容回滚 | `ContentRevision` 已保存 `before` / `after` 完整快照，补一个 apply 接口即可 |
| 多语言 | 内容表加 `locale` 字段并纳入唯一键 |
| 图片迁 OSS | `MediaAsset.path` 语义不变，只替换 `StorageService` 实现 |
| 全文检索 | 给 `Country.summary` / `Attraction.name` 加 GIN 索引或接入搜索服务 |
| 分库分表 | 首版单机 PostgreSQL 足够，`Trip` / `PlanItem` 是最可能的增长点 |
