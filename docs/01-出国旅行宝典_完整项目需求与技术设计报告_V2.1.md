## 1. 项目概述

### 1.1 产品名称

**出国旅行宝典**

### 1.2 产品定位

《出国旅行宝典》是一款面向出境自由行用户的旅行全流程管理应用，覆盖旅行目的地探索、国家旅行信息查询、签证与入境准备、行前物品准备、航班与酒店管理、多国家及跨大陆旅行计划、景点路线规划、旅行过程打卡、照片与感悟记录、历史旅行沉淀以及旅行海报生成。

产品不是单纯的“旅游攻略”，而是把攻略信息转化为可以直接执行的个人旅行计划。

核心链路：

```text
发现目的地
↓
查看国家攻略
↓
把攻略内容加入旅行计划
↓
按照阶段执行旅行
↓
旅行过程中记录路线和回忆
↓
完成旅行
↓
沉淀个人旅行档案
```

核心理念：

> **地图负责发现，攻略负责决策，计划负责执行，个人页负责沉淀。**

## 2. 核心产品原则

### 2.1 Trip 是核心对象

一次旅行不是一个国家，而是一段完整旅程。一条 Trip 可以包含 1 个或多个国家，也可以横跨多个大陆，并包含多个城市、旅行人员、航班、酒店、景点和计划任务。

示例：

```text
日韩自由行
2026.10.01 - 2026.10.12

🇯🇵 日本
↓
🇰🇷 韩国
```

也可以：

```text
环球旅行

🇯🇵 日本 · 亚洲
↓
🇺🇸 美国 · 北美洲
↓
🇫🇷 法国 · 欧洲
```

### 2.2 攻略与计划分离

国家详情页中的签证材料、交通建议、物品准备、推荐 App、景点等属于公共攻略内容。只有用户主动点击 `＋` 后，才转化为当前 Trip 中的个人 PlanItem。

### 2.3 `＋ / ✓` 必须与真实数据同步

```text
未加入：＋
点击后：✓
再次点击：直接移除
```

移除后显示：

```text
已从计划移除  [撤销]
```

`＋ / ✓` 状态不能只保存在页面 UI 中，必须来自当前 Trip 的真实计划数据。

### 2.4 当前阶段优先

旅行计划分为：

```text
准备阶段
↓
出发阶段
↓
旅行阶段
↓
归程阶段
```

四个阶段始终展示，但只有当前阶段展开详细内容。

### 2.5 内容与表现分离

后台负责“显示什么内容”，客户端负责“内容长什么样”。后台不使用 HTML 或大段富文本直接控制客户端 UI，而应返回结构化 JSON。

### 2.6 多端共享业务逻辑

微信小程序、后续 React Native App、后台与后端尽可能共享 TypeScript 类型、枚举、API Client 和纯业务逻辑，避免相同规则在不同端重复实现。

## 4. Tab 1：地图页

### 4.1 页面目标

地图页负责：

> **探索大陆 → 发现国家 → 进入国家详情 → 加入旅行**

### 4.2 3D 地球设计

地图页中心展示一个淡蓝色、半透明、带毛玻璃质感和空间层次的视觉 3D 地球，支持左右拖动旋转。

首版不追求真实卫星地图、高精度国界、真实地形、实时云层、复杂 Shader 或重型 WebGL 场景。

### 4.3 推荐实现

首版优先：

```text
Canvas
+
球面投影
+
2D 大陆矢量数据
+
渐变
+
光晕
+
遮挡
+
惯性动画
```

目标是：**视觉像 3D，交互必须丝滑。**

### 4.4 本地地理数据

用于首屏绘制和 3D 地球初步交互的数据必须随客户端打包，不依赖网络。

建议：

```text
assets/geo/
├── continents.min.json
├── continent-centers.json
└── country-points.json
```

保存：大陆轮廓、大陆中心点、国家点位、国家所属大陆关系、首屏默认观察参数。

启动流程：

```text
打开小程序
↓
读取客户端本地数据
↓
立即绘制地球
↓
立即可以旋转
↓
后台异步拉取业务数据
```

### 4.5 大陆交互

支持亚洲、欧洲、非洲、北美洲、南美洲、大洋洲。

```text
自动轻微旋转
↓
用户触摸
↓
停止自动旋转
↓
左右拖动
↓
惯性旋转
↓
减速
↓
吸附最近大陆
```

当前大陆高亮，其他大陆弱化。

### 4.6 性能目标

优先级：

```text
流畅度 > 视觉效果 > 真实度
```

目标：中端手机尽量达到 60 FPS，无法达到时保证稳定 30 FPS。性能不足时可自动降低大气层动态、粒子、阴影等效果，但拖动、旋转、大陆吸附、国家选择不得受影响。

### 4.7 国家列表

选择大陆后展示国家列表，每个国家可包含国旗、中文名、英文名、签证状态、是否加入当前 Trip、是否去过等信息。

### 4.8 当前旅行区域

```text
当前旅行

🇯🇵 日本
↓
🇰🇷 韩国

＋ 添加国家
```

用户可以继续旋转地球，在其他大陆添加新的国家。

## 6. 国家详情页操作提示

只要用户没有关闭提示，每次进入国家详情页都弹出：

> 页面中的签证材料、准备物品、景点等内容旁带有「＋」，点击即可加入本次旅行对应阶段。添加后「＋」会变成「✓」，再次点击即可移除。

按钮：

```text
[确认]
[以后不再提示]
```

点击“确认”只关闭本次弹窗，`showPlanAddGuide` 仍为 `true`，下次仍提示。

点击“以后不再提示”：

```ts
showPlanAddGuide = false
```

设置页提供重新开启入口：

```text
我的
→ 设置
→ 操作提示
→ 国家攻略加入计划提示
```

## 9. 签证模块

### 9.1 内容结构

签证 UI 不参考已有示例图，但内容结构参考该示例。至少包含：签证结论、核心政策、最长停留、签证费用、办理时间、所需材料、注意事项、信息来源、更新时间。

### 9.2 签证政策匹配

签证政策不是 `Country → Visa`，而是：

```text
PassportRegion
+
DestinationCountry
→
VisaPolicy
```

例如：

```text
CN → JP
SG → JP
```

### 9.3 用户默认证件地区

默认：

```text
中国大陆
CN
```

用户可在：

```text
我的
→ 个人资料
→ 护照所属国家/地区
```

修改。

### 9.4 签证材料

只有可执行内容显示 `＋`。

```text
护照原件
有效期至少 6 个月     ＋

返程机票行程单        ＋

酒店预订确认单        ＋
```

纯信息例如“最长停留 60 天”不显示 `＋`。

> **结构化旅行知识库管理系统。**

# 30. 媒体存储

## 30.1 当前方案

前期直接使用阿里云 ECS 本地文件系统。

建议：

```text
/data/travel-guide/uploads/
```

不要放在代码目录中。

## 30.2 客户端访问方式

客户端不能看到服务器真实路径。

服务器文件：

```text
/data/travel-guide/uploads/attractions/jp/a.webp
```

通过 Nginx 暴露：

```text
https://api.example.com/static/attractions/jp/a.webp
```

客户端只使用 URL。

## 30.3 用户图片处理规则

所有用户上传图片：

```text
上传
↓
格式校验
↓
解码
↓
调整最大分辨率
↓
压缩
↓
转换格式
↓
保存压缩后文件
↓
丢弃原图
```

例如：

```text

处理后：1600 × 1200，WebP，约 300～700 KB
```

首版每张图只保存一个压缩后的主版本。

## 30.4 上传限制

# 40. Monorepo

## 40.1 定义

Monorepo 指：

> **一个 Git 仓库中同时管理多个应用和共享代码包。**

建议结构：

```text
travel-guide/

apps/
├── miniapp/
├── admin/
├── api/
└── mobile/

packages/
├── core/
├── types/
├── api-client/
├── constants/
└── utils/
```

## 40.2 apps

`apps` 保存可以独立运行和部署的应用：

- miniapp：微信小程序
- admin：React 后台
- api：NestJS API
- mobile：React Native App

## 40.3 packages

`packages` 保存多个应用共享的**源代码**。

通常开发维护的是：

```text
src/
```

编译后的：

```text
dist/
```

由构建工具自动生成，一般不提交 Git。

# 41. packages/core

`core` 保存与 UI、数据库、网络、平台无关的纯业务逻辑。

建议：

# 75. 主 Tab 导航架构：单页 Shell + 自定义悬浮 TabBar

## 75.1 设计决策

微信小程序主导航不使用微信原生 `tabBar`，改为自定义的 `FloatingTabBar`。

三个主 Tab：

```text
地图
计划
我的
```

全部由同一个：

```text
pages/dashboard
```

页面承载。

主 Tab 切换时禁止使用：

```text
navigateTo
redirectTo
switchTab
reLaunch
```

主 Tab 之间只修改：

```ts
activeTab
```

从而避免：

- 页面重新创建
- 白屏刷新
- 状态丢失
- 3D 地球重新初始化
- 不必要的接口请求
- 主 Tab 之间跳转割裂感

这一架构只针对三个主 Tab。

国家详情、Trip 详情、编辑表单、景点详情等二级页面仍可正常使用 Taro 路由能力。

# 76. Dashboard 页面结构

页面关系：

```text
Dashboard / Shell
│
├── 横向 Tab Stage
│   ├── 地图 Tab
│   ├── 计划 Tab
│   └── 我的 Tab
│
└── FloatingTabBar
```

三个 Tab 页面始终挂载在 Dashboard 中。

优势：

1. 切换 Tab 时不会卸载页面。
2. 地图状态可以保持。
3. 计划页列表状态可以保持。
4. 个人页内容不会反复重新加载。
5. 后续可以保存不同 Tab 各自的滚动位置。
6. 更接近 iOS 原生 Tab 的连续体验。

# 77. 横向滑动容器

主内容区域采用横向 Flex 容器。

核心结构：

```scss
.tabStage {
  display: flex;
}

.tabPane {
  width: 100vw;
  flex-shrink: 0;
}
```

根据当前 `activeTab` 计算索引：

```ts
const activeIndex = tabs.findIndex(
  item => item.key === activeTab
)
```

然后：

```ts
transform: `translate3d(-${activeIndex * 100}vw, 0, 0)`
```

动画统一使用：

```css
cubic-bezier(0.22, 1, 0.36, 1)
```

推荐：

```css
transition:
  transform 420ms cubic-bezier(0.22, 1, 0.36, 1);
```

并增加：

```css
will-change: transform;
```

降低连续切换过程中的卡顿概率。

# 78. Tab 页面滚动模型

为了避免横向 Flex 容器被“最高的那个 Tab”撑高，从而导致其他短页面出现大面积无意义空白，各 Tab 使用独立纵向滚动容器。

结构：

```text
dashboardShell
  ↓
tabViewport
  ↓
tabStage
  ↓
tabPane
  ↓
ScrollView
```

每个 `.tabPane` 占满可用视口，但内部实际内容高度保持自然。

因此：

- 内容少时不会人为生成很长页面；
- 内容多时只在当前 Tab 内自然纵向滚动；
- 三个 Tab 可以分别维护自己的滚动位置；
- 横向切换不会受到其他 Tab 内容高度影响。

所有 Tab 内容底部统一预留足够安全距离：

```css
padding-bottom: 200px;
```

避免被 FloatingTabBar 遮挡。

FloatingTabBar 使用 iOS 风格悬浮玻璃胶囊。

- `position: fixed`
- 底部悬浮
- 左右留边
- 大圆角
- 半透明白色玻璃背景
- `backdrop-filter`
- `-webkit-backdrop-filter`
- 边缘使用轻微白色描边
- 增加柔和阴影
- 考虑 iPhone Safe Area

```css
bottom: calc(18px + env(safe-area-inset-bottom));
```

- 淡蓝色高亮胶囊
- Active 图标使用淡蓝色版本图片
- 文字为淡蓝色

未激活状态：

- 浅灰色图标
- 浅灰色文字

建议准备：

# 86. 主 Tab 页面生命周期原则

三个主 Tab 在 Dashboard 中同时挂载。

因此切换：

```text
地图
→
计划
→
地图
```

默认不会触发地图组件重新创建。

这一点对 3D 地球特别重要。

必须避免：

```text
Tab 切换
↓
Canvas 销毁
↓
重新加载 GeoJSON
↓
重新绘制
```

正确行为：

```text
首次进入 Dashboard
↓
初始化 3D 地球
↓
之后只切换横向位置
↓
地球实例继续保留
```

# 87. Tab 数据加载策略

虽然三个页面同时挂载，但不建议启动时立即请求三个 Tab 的全部数据。

建议：

```text
Dashboard 初始化
↓
优先初始化 Map
↓
其他 Tab 延迟加载
```

Store 为每个模块维护：

```ts
initialized
loading
lastUpdatedAt
```

例如：

```text
首次点击计划
↓
planStore.initialized == false
↓
加载当前 Trip
↓
initialized = true
```

以后再次切换计划：

```text
直接展示 Store 中现有数据
```

后台刷新则依赖之前定义的：

- 缓存
- 内容版本
- Service

机制。

# 93. 动画与性能要求

主 Tab 横向动画：

```css
transition:
  transform 420ms cubic-bezier(0.22, 1, 0.36, 1);
```

强制使用：

```css
translate3d()
```

而不是：

```css
left
margin-left
```

原因：

- 更容易进入 GPU 合成层
- 减少 Layout
- 降低主线程抖动

同时：

```css
will-change: transform;
```

仅用于 `.tabStage`。

不要给大量普通组件滥用 `will-change`。

# 94. 3D 地球与 Dashboard 的性能配合

地图 Tab 的 3D 地球虽然保持挂载，但当当前 Tab 不是地图时，可以暂停：

```text
自动旋转
requestAnimationFrame 动画
非必要动态效果
```

例如：

```ts
isActive = activeTab === 'map'
```

传入地图模块：

```tsx
<MapTabContent active={activeTab === 'map'} />
```

地图模块：

```text
active = true
→ 恢复动画

active = false
→ 暂停动画
```

注意：

> 暂停动画不等于销毁 Canvas。

这样既保证切回来立即恢复，又减少后台 Tab 的 CPU / GPU 消耗。

# 96. 本次新增架构决策
