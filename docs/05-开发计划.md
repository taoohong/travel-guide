## 1. 阶段划分与实施顺序

需求文档第 67 章给出的推荐顺序为：

```text
1. Monorepo 初始化 → 2. packages/types → 3. Prisma 数据模型 → 4. NestJS 基础 API
→ 5. packages/api-client → 6. packages/core → 7. 后台 CMS → 8. 内容版本机制
→ 9. 小程序 Store/Service/Cache → 10. Trip/Plan → 11. 国家详情 → 12. 3D 地球
→ 13. 旅行路线 → 14. 旅行回忆 → 15. 海报
```

本仓库在实现时做了一处**工程优化**：把 `packages/core`（纯业务逻辑）提前到 Prisma 之前，
因为 core 是被后端、小程序、App、后台**共同依赖**的最底层，先固化它可以避免后续返工。

```text
最终实际依赖顺序：

constants → types → utils → core → api-client
                                   ↓
                    ┌──────────────┼──────────────┐
                    ↓              ↓              ↓
               apps/api      apps/miniapp    apps/admin / apps/mobile
```

## 2. P0：Monorepo 与共享层

**目标**：一个 Git 仓库管理多个应用与共享源代码包（文档第 40～46 章）。

**交付物**

```text
pnpm-workspace.yaml           # packages: apps/* packages/*
tsconfig.base.json            # 全仓 TS 基线（strict）
vitest.config.ts              # 统一测试配置
eslint.config.mjs             # 代码规范
packages/constants/           # TripStatus / PlanStage / PlanItemType / VisaType ...
packages/types/               # Country / VisaPolicy / Trip / TripDestination / PlanItem / Attraction
packages/utils/               # 日期、字符串、校验、Result、错误类型
```

**关键决策**

1. `packages/*` 只暴露 `src/`，`dist/` 由构建工具生成且不提交 Git。
2. 所有包通过 `workspace:*` 相互引用。
3. TypeScript 全量 `strict`，并开启 `noUncheckedIndexedAccess`，把「可能取到 undefined」的
   情况在编译期暴露——这正是签证/景点等数组处理的常见 bug 源头。

**验收**：`pnpm -r typecheck` 通过；`pnpm test` 中 constants/types/utils 用例全绿。

## 3. P1：核心业务逻辑层 `packages/core`

**目标**：把文档第 68 章「核心业务规则清单」逐条落成**纯函数**，不引入任何 Taro / React / Prisma / HTTP。

**模块与规则映射**

| core 模块 | 覆盖的规则（文档章节） |
|---|---|
| `trip/tripStage.ts` | 规则 13/14：四阶段；当前阶段判定；`DRAFT→…→COMPLETED` 状态机（第 19 章） |
| `trip/tripDestination.ts` | 规则 2/3/4：Trip 多国家、跨大陆；大陆只是浏览分类 |
| `trip/tripStageSwitch.ts` | 第 15 章：**系统提示 + 用户确认**，不做日期自动切换 |
| `plan/planItem.ts` | 规则 7/8/9/10/11/12：PlanItem 实体、来源追踪、scope、dedupeKey |
| `plan/planDedupe.ts` | 规则 12：`buildDedupeKey` / `isDuplicatePlanItem` |
| `plan/planToggle.ts` | 第 7 章：`＋/✓` 添加、删除、撤销（Undo Token） |
| `plan/planProgress.ts` | `calculatePlanProgress()` 进度计算 |
| `plan/planFromGuide.ts` | 第 24 章：`planMapping` → PlanItem 草稿（决定是否显示 `＋`、落到哪个阶段） |
| `visa/visaPolicy.ts` | 规则 20：`PassportRegion + DestinationCountry → VisaPolicy` |
| `visa/visaPriority.ts` | 签证候选策略优先级（精确 > 区域 > 通用兜底） |
| `visa/visaExpiry.ts` | 第 33 章：`effectiveFrom/effectiveTo/lastVerifiedAt`、90 天未确认 |
| `destination/grouping.ts` | 第 10 章：去程 / 跨国 / 回程归属阶段（规则 15/16/17） |
| `itinerary/itinerary.ts` | 第 14.4 章：按天路线、景点排序、打卡时间线 |
| `content/contentVersion.ts` | 第 52/53 章：**逐模块**比较版本，只刷新变化的模块 |
| `content/contentHealth.ts` | 第 34 章：内容完整度、健康度看板指标 |
| `content/guidePrompt.ts` | 第 6 章：`showPlanAddGuide` 提示状态机（确认 vs 不再提示） |
| `common/` | `Result`、分页、排序等通用纯逻辑 |

**设计要点**

- 所有函数**输入普通数据、输出普通数据**，因此可以在 Node、小程序、App 三端直接跑。
- 输入一律做**防御性校验**：`undefined` 列表、缺字段、非法枚举都不抛异常，返回安全默认值或 `Result.fail`。
- 规则常量（90 天、6 个月护照有效期等）集中放在 `core/constants` 便于统一调整。

**验收**：`packages/core` 单测覆盖每条规则清单，含边界用例（空 Trip、跨大陆、同日多打卡、去重冲突）。

## 4. P2：API 客户端 `packages/api-client`

**目标**：小程序与 React Native **共用**同一套 API 封装（文档第 43 章）。

**交付物**

```text
src/http.ts           # fetch 适配器接口（可注入 Taro.request / wx.request / RN fetch）
src/errors.ts         # ApiError：网络错误 / 超时 / HTTP 状态 / 业务错误码 四类
src/retry.ts          # 指数退避 + 抖动；只重试幂等请求
src/timeout.ts        # AbortController 超时兜底（兼容不支持 AbortSignal 的运行环境）
src/endpoints/*.ts    # country / visa / attraction / trip / plan / user / content-version
```

**兜底机制（异常处理重点）**

| 场景 | 行为 |
|---|---|
| 网络不可达 | 抛 `ApiError(kind='NETWORK')`，`isRetryable=true`，由上层决定用缓存 |
| 请求超时 | `ApiError(kind='TIMEOUT')`，默认 10s，可配置 |
| 401 | 触发注入的 `onUnauthorized` 回调（清 token / 重新登录） |
| 429 / 5xx | 自动重试（指数退避 + 抖动），退避上限可配 |
| 4xx 业务错误 | **不重试**，解析后端统一错误体中的 `code/message/details` |
| 响应体不是 JSON | 抛 `ApiError(kind='PARSE')`，不会把 HTML 错误页当成数据 |
| `AbortController` 不存在 | 降级为 `Promise.race` 定时器，保证超时仍然生效 |

**关键决策**：`packages/api-client` **不直接依赖** `Taro.request`。
它只依赖一个 `HttpAdapter` 接口，小程序端注入 Taro 适配器，App 端注入 fetch 适配器。
这样这个包本身可以在 Node 里被完整单测。

## 5. P3：后端 API `apps/api`

**目标**：NestJS + Prisma + PostgreSQL，作为唯一数据出口（文档第 57～59 章）。

**交付物**

```text
prisma/schema.prisma          # 全量数据模型（第 20～35 章）
prisma/seed.ts                # 示例数据（日本/韩国/法国 + 签证 + 景点 + 交通 + 物品 + 贴士）
src/common/                   # 统一响应、异常过滤器、日志、分页、Zod 校验管道
src/modules/auth/             # 管理员登录 + JWT + 角色守卫（第 37 章四种角色）
src/modules/continent|country|city/
src/modules/visa/             # 按 passportRegion + destinationCountry 维护（第 25 章）
src/modules/transport|packing|tip|attraction/
src/modules/trip|plan/        # Trip / TripDestination / PlanItem / Memory
src/modules/content-version/  # 分模块版本号 + 递增（第 52 章）
src/modules/media/            # 上传 + 压缩 + WebP + StorageService 抽象（第 30/59/61 章）
src/modules/operation-log/    # 操作日志（第 38 章）
src/modules/content-health/   # 健康度看板（第 34 章）
```

**异常处理（异常处理重点）**

1. `AllExceptionsFilter` 把一切异常统一成：
   `{ code, message, details, requestId, timestamp }`，客户端只解析一种格式。
2. Prisma 错误码映射：`P2002` → 409 唯一冲突、`P2025` → 404 记录不存在、`P2003` → 400 外键。
3. 全局 Zod 校验管道：请求体不合法 → 400 且返回**字段级**错误明细。
4. 上传：文件缺失 / 类型不支持 / 超过 5 MB / 解码失败 / 磁盘写入失败，各自给出明确错误码。
5. **图片处理失败时不留脏文件**：写入临时文件 → 处理成功才移动；失败则清理临时文件。
6. 数据库不可用：启动时不 panic，健康检查 `/api/v1/health` 明确报告 DB 状态。

**媒体存储抽象（第 61 章）**

```ts
interface StorageService { upload(); delete(); getUrl(); }
```

首版 `LocalStorageService` 落 `/data/travel-guide/uploads`，未来换 `AliyunOSSStorageService` 时业务代码零改动。

## 6. P4：后台 CMS `apps/admin`

**目标**：**结构化旅行知识库管理系统**，不是数据库编辑器（第 20.1 章）。

**交付物**：React + TS + Ant Design 骨架，含登录、内容健康度首页、国家列表、
签证政策编辑（含 `planMapping` 结构化配置）、媒体上传、操作日志。

**关键决策（第 2.5 章「内容与表现分离」）**

后台**不返回 HTML / 富文本**，只维护 **结构化 JSON 字段**：

```ts
planMapping: { actionable, targetStage, itemType, scope, dedupeKey }
```

客户端根据 `planMapping` 自行决定「显示什么样子」，后台只管「内容是什么」。

## 7. P5：小程序 `apps/miniapp`

**目标**：Taro + React + TypeScript，微信小程序首发。

**交付物**

```text
src/app.config.ts                 # 不配置原生 tabBar（第 90 章）
src/components/FloatingTabBar/    # iOS 玻璃胶囊悬浮 TabBar（第 79～83 章）
src/pages/dashboard/              # 单页 Shell，三 Tab 常驻挂载（第 75～88 章）
src/features/map/                 # 3D 地球 + 大洲 + 国家列表
src/features/plan/                # 四阶段计划
src/features/profile/             # 我的 / 历史旅行
src/pages/destination-detail/     # 国家详情（二级页面，正常路由）
src/canvas/globe/                 # 球面投影、遮挡、惯性、吸附（纯函数 + 渲染分离）
src/stores/                       # 按领域拆分 Zustand store（第 49 章）
src/services/                     # 缓存判断 + API 调用 + 组合（第 50 章）
src/cache/                        # 分模块缓存 + cacheKeys（第 51/55 章）
src/assets/geo/                   # 随包打包的地理数据（第 4.4 章）
```

**3D 地球实现要点（第 4.3/4.6 章）**

- 视觉像 3D，交互必须丝滑：`Canvas + 球面投影 + 2D 矢量大陆 + 渐变 + 光晕 + 遮挡 + 惯性`。
- **投影数学与渲染完全分离**：`globeProjection.ts` 是纯函数（可单测），`globeRenderer.ts` 只画。
- 拖动 → 惯性 → 减速 → **吸附最近大陆**；触摸即停止自动旋转。
- 性能降级：`qualityLevel = high | medium | low`，低端机自动关闭大气层/粒子/阴影，
  但**拖动、旋转、吸附、选择国家**永不降级（第 4.6 章硬性要求）。
- 切走地图 Tab 时 `requestAnimationFrame` 暂停但 **Canvas 不销毁**（第 94 章）。

**缓存与版本同步（第 51～55 章）**

- Cache First + Background Refresh。
- 打开页面：先读本地缓存立即渲染 → 后台比对 `contentVersion` → 只刷新变化的模块。
- 签证缓存 key **必须**含护照地区：`visa_CN_JP`，用户改护照地区后使相关缓存失效。

**状态分层（第 48～50 章）**

```text
Page → Component → Store/Zustand → Service → Cache → api-client → Backend
```

Store **不做**底层请求细节；Service 负责缓存判断与编排。

## 12. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 地球性能不达标 | 首屏体验崩塌 | 纯函数投影 + 分级画质 + Tab 切换暂停 rAF；本地地理数据不依赖网络 |
| 签证政策过期 | 误导用户 | `effectiveFrom/To + lastVerifiedAt`，后台 90 天未确认告警 |
| 攻略内容重复 | 计划里出现 3 个「护照」 | `dedupeKey` + Trip 级去重，后端加唯一约束兜底 |
| 图片撑爆磁盘 | 服务不可用 | 上传即压缩、丢弃原图、单文件 5 MB 上限、目录按国家分片 |
| 多端逻辑漂移 | 三端行为不一致 | 规则全部下沉到 `packages/core`，各端只写 UI |
| 后期换 OSS | 大范围改代码 | `StorageService` 抽象，业务代码不感知存储实现 |
